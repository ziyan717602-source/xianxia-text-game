# 仙侠文字游戏（A Dark Room-like）项目综合审核报告

基于当前的代码库状态、游戏设计的初衷（渐进揭示、反坐牢、淡然旁观）以及仙侠题材的合理性，我对本项目进行了深度审核。以下是审核发现的问题及优化建议：

---

## 1. 仙侠题材契合度 (Thematic Consistency)

正如您所察觉的，像“读书”这样的行为在仙侠语境下确实显得有些违和（更偏向科举或武侠）。我们需要将用词和概念替换为更符合“修道”体系的术语，让玩家更有代入感。

| 当前设定 / 变量 | 存在的问题 | 建议的仙侠化修正 |
| :--- | :--- | :--- |
| **读书 (dushu)** | 凡俗气过重，修仙者不只是看文字，更重悟道。 | **参悟 (Comprehend)** 或 **观想 (Visualize)**。如果是凡人开局，可以是 **研读残卷**。 |
| **见闻 (knowledge)**| 像是在写江湖游记，无法与“功法”、“境界”直接挂钩。 | **悟性** 或 **神识 (Spiritual Sense)** 或 **道蕴**。代表对天地的理解。 |
| **休息 (xiuxi)** | 过于白话。 | **静心 / 调息 (Rest/Meditate)** |
| **钱币 (coins)** | 前期凡人阶段合理，但在突破炼气后，继续用银两会很出戏。| 底层数据保留 `coins`，前端显示在凡人期为**银两**，进入修仙界后解锁/转化为**灵石**。 |
| **草药 (herbs)** | 概念宽泛。 | 凡人期为**草药**，修仙期为**灵草**。 |
| **体力 (stamina)** | 修真者不仅消耗肉身力量，更消耗精神。 | **精元 / 心神 (Essence/Mind)** |

---

## 2. 游戏设计角度 (Game Design: A Dark Room 范式)

项目目标是借鉴《A Dark Room》（小黑屋）的“渐进揭示”机制，但当前的 UI 和底层实现并没有完全贯彻这一原则。

### 🚨 问题 1：数值面板过早全盘暴露 (Information Overload)
目前玩家一开局，UI 就展示了：`体力: 100, 真气: 0, 寿元: 60年, 草药: 0, 钱币: 0, 见闻: 0, 伤势: 0`。
这破坏了探索感。小黑屋的精髓在于“起初只有一堆火，后来才有了木头、陷阱、村庄”。

**🛠️ 改进方案**：
- **资源隐匿机制**：前端 UI 只渲染**曾经大于 0** 的资源。
- 开局界面应该极其极简。例如，开局只有一行字：“破庙漏雨，寒风刺骨。” 和一个按钮：【生火】或【枯坐】。
- 只有当玩家第一次获得“真气”时，左侧栏才突兀地浮现“真气：1”的字样。
- “寿元”这个核心压力，应该在玩家第一次经历时间跨度较大（比如闭关/重伤沉睡），或者突破大境界时，才赫然出现在面板上，给予玩家震撼。

### 🚨 问题 2：资源的无限堆叠与“坐牢”感
当前 Tick 引擎设定 1 Tick 恢复 1 点体力，吐纳消耗 10 体力产出 1 真气。玩家可以盯着屏幕，每隔 10 秒点一次“吐纳”。这种频繁的机械点击极易变成“坐牢”。

**🛠️ 改进方案**：
- 落实 `AGENTS.md` 中的“反坐牢”设计：引入**阵法/聚灵阵**或**周天运转**系统。
- 当玩家手动“吐纳”达到一定次数（如 20 次），解锁【自动运转小周天】，每 Tick 自动消耗微量精元产出真气。玩家的操作重心应该迅速从“点按钮获取资源”转移到“分配资源”上。

## 3. 游玩进程 (Gameplay Progression)

当前的开局进程存在一定逻辑跳跃，为了修复卡死临时加入的 `['dushu', 'xiuxi']` 只是权宜之计，缺乏叙事张力。

### 🎬 重新设计的开局 Flow 提议：
1. **初始状态**：无任何资源显示。只有一个行动：`【枯坐】`。日志：“你是一名凡俗扫地小厮，不知何为仙。”
2. **枯坐几次后**：解锁事件“柴房的旧物”。玩家在柴堆里翻到一个残破的玉简（或者遇到重伤的散修）。
3. **获得机缘**：玉简割破手指，神识刺痛。此时面板第一次解锁资源：`神识: 1`。并解锁行动：`【探查玉简】`。
4. **探查玉简**：消耗大量体力，获得信息。解锁行动：`【吐纳】`。
5. **首次吐纳**：日志显示“一丝微凉的气息游走全身”。左侧面板解锁：`真气: 1` 和 `精元: 90`（由于消耗）。
6. **精元耗尽**：当精元不足时，日志提示“心力交瘁”，解锁：`【调息】`（消耗时间/寿元换取精元快速恢复）。

## 4. 软件开发架构 (Software Architecture)

代码底子打得不错，逻辑和 UI 分离明确，Vitest 测试覆盖了基础逻辑，但在以下几处埋有隐患：

1. **离线进度的性能炸弹**：
   `tick.ts` 中的 `while (ticksToProcess > 0)`。如果玩家离线了 1 天（86400 秒），重连时会同步执行 86400 次循环（包括深拷贝 State、触发判定）。这会导致浏览器直接卡死崩溃。
   - **优化**：需要将 Tick 改为数学公式结算（Bulk Processing），即 `newState.qi += offlineTicks * qiPerTick`，而不是使用 while 循环。
2. **React 渲染性能**：
   每 1000ms 触发一次 `setGameState`。由于 `GameState` 嵌套较深，每次 `setGameState` 导致整个 `<App />` 重新渲染。目前组件很少没问题，但后期挂件多时会卡顿。
   - **优化**：后续开发中应当将各个面板（资源面板、日志面板）拆分为独立的子组件，并使用 `React.memo` 或者引入 `Zustand` 局部订阅来避免不必要的 Re-render。
3. **事件数据中的函数序列化**：
   `activeEvent.text` 可能是函数。虽然没有保存在 LocalStorage 中（存的是 ID），但未来若有动态生成的事件参数（如“遇到了随机名字的 NPC”），仅存 ID 是不够的，需要引入 `EventContext` 存储运行时变量。

2. 在 UI 层面实现**资源渐进揭示机制**（只渲染有过变动、或达到特定条件的资源）。
3. 用上述提议的“枯坐->发现玉简->吐纳”的叙事流替换掉当前的粗糙开局。
