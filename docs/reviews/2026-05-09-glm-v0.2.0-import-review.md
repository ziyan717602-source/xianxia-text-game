## 分支规则

- `main`：稳定主线，只放已审查、已验证、符合当前设计方向的内容。
- `glm/v0.2.0-snapshot`：GLM 原样快照，只读留档，不在该分支上继续开发。
- `integration/glm-v0.2.0`：后续整合分支，从 `main` 出发，按系统小步吸收 GLM 内容。
- `codex/*`：Codex 新功能或修复分支。

禁止做法：

- 不从 GLM 目录直接覆盖 `C:\个人\文字冒险`。
- 不把 `glm/v0.2.0-snapshot` 直接 merge 到 `main`。
- 不把大批内容、工程规则、UI 和存档迁移混在一个提交里合入。

推荐做法：

1. 每次只挑一个系统，例如道途、心魔、宗门、秘境或飞升。
2. 先读 GLM 快照中的实现和测试，再判断是否直接移植、重写或放弃。
3. 先补类型、状态账本和存档迁移，再接行动、事件和 UI。
4. 每个系统必须有对应测试和文档更新。
5. 合入前至少跑 `npm test`、`npm run build`，涉及 UI 或浏览器流程时再跑烟测。

## 建议吸收顺序

1. 修复/统一烟测方案：先决定继续使用当前 CDP 烟测，还是引入 Playwright 并把依赖写清。
2. 小型账本系统：优先审查 `daopath`、`karma`、`innerDemon`，它们符合“行为形成道途”和“后果账本”的方向。
3. 存档结构与迁移：GLM 扩展了大量 `GameState` 字段，必须先做版本迁移和旧存档兼容。
4. 宗门与洞府：和当前阶段方向相近，但需避免过早职业锁定和资源膨胀。
5. 秘境与飞升：作为中后期主线，等前置账本稳定后再接。
6. 大量地点、丹方、功法和高境界内容：最后筛选，避免一次性堆内容压垮数值和 UI。
