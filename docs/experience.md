# 开发经验记录

更新时间：2026-05-06

这份文档用于持续记录本项目和其他游戏/程序开发可复用的方法、工具、提示词和踩坑。每次完成阶段性工作后更新。

## 已验证经验

- 先写项目级 agent 指令，再让 AI 开发游戏代码。这样能减少版权、架构和测试方向漂移。
- 对文字增量游戏，核心逻辑必须可测试；UI 截图无法证明资源循环正确。
- 修仙题材适合把“资源增长”包装成“修行代价”：丹毒、心魔、因果、天劫比单纯货币更有辨识度。
- 远程仓库建立前也应先初始化本地 git，并在文档里记录云端步骤，避免早期文件散落。
- 未审计的第三方 skills 不直接安装。优先官方 curated skills；项目特化能力用本地 skill 自建。

## 推荐提示词模板

### 实现玩法前

```text
请先阅读 agents.md、docs/game-design.md、docs/experience.md。
我要实现 [系统名]。先给出资源流、解锁条件、失败/代价、测试点，再修改代码。
不要使用任何现有仙侠 IP 的专有名称或剧情。
```

### 数值调优

```text
请检查 [资源/系统] 的前 10 分钟节奏。
目标是 [更快解锁/减少等待/增加选择压力]。
输出需要包含：调整原因、改动文件、验证方法、可能副作用。
```

### Bug 修复

```text
请复现并修复这个问题：[现象]。
先定位是否属于状态模拟、存档迁移、UI 渲染或事件触发。
修复后运行相关测试，并说明未覆盖风险。
```

## 工具记录

- Codex：适合整体规划、文件编辑、测试和仓库维护。
- Playwright / browser testing：适合验证本地 Web 游戏是否能点击、存档、刷新恢复。
- GitHub/Cursor/Claude Code：通过仓库指令文件保持一致行为。
- Web 调研：只把机制级经验写入仓库，避免搬运受版权保护的文本和设定。
